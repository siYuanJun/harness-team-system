# Harness Team Mission Planner

## 概述

本 Skill 将一个里程碑需求转化为一整套可执行的多 Agent 任务指令文件夹。生成的指令可以直接交给 Claude Code 执行，Claude Code 会扮演 orchestrator 调度团队各角色完成任务。

## 使用场景

- 用户提出一个新的里程碑需求（如"M4 数字员工躯体部署"）
- 需要为 Harness 团队规划任务分工、阶段划分、质量门
- 需要产出可直接交给 Claude Code 执行的启动指令（LAUNCH.md）
- 需要保持和已有里程碑一致的任务指令结构

**前置条件**：当前项目已有 Harness 团队（`.claude/agents/`），或 `harness/` 下有可用团队源。如果团队不存在，本 Skill 会提示先用团队搭建方法论创建团队（见第二步）。

## 核心流程

### 第一步：需求解析
- 提取：里程碑目标、当前状态、阻塞项、验收标准
- 确定：任务类型（开发/测试/部署/调研）、预计复杂度
- 判断：是否需要前置检查与修复（如依赖未安装、接口未接通先补再测）

### 第二步：团队检测与匹配
- 检查当前项目是否有 `.claude/agents/` 目录
- 有 → 读取角色定义，用当前项目的团队
- 没有 → 检查 `harness/` 下是否有可用团队源目录（如 ontology-brain-team、hermes-agent-team），列出让用户指定
- 如果 `harness/` 下也没有合适的团队，或用户想为当前项目**新建团队** → 停止生成任务指令，明确提示用户：
  > 当前项目没有 Harness 团队。请先用团队搭建方法论创建团队：
  > 见本仓库 `_methodology/team-building-methodology.md`
  > 按该方法论的 9 步流程搭建团队后，再回到本 Skill 生成任务指令。
- 提取目标团队的角色名、职责、路由关系，生成时角色名必须和目标团队完全匹配

### 第三步：阶段设计与质量门
- 通常 3 阶段：阶段0（PM‖ENG 并行）→ 阶段1（APP 主执行）→ 阶段2（QA 独立验收）
- 根据任务类型调整阶段数和角色参与（如纯开发任务可合并阶段0和1）
- 设计 3 道质量门，每门有明确、可验证的通过条件

### 第四步：生成各角色指令
- 每个角色指令包含：任务 / 交付物 / 具体要求 / 验收标准 / 工作方式 / 记住
- 角色名用目标团队的实际名称（如 brain-pm、hermes-reviewer）
- PM：定标准 + 样本/方案设计
- ENG：修配置 + 冒烟
- APP：主执行 + 出报告
- QA：独立验收 + 反作弊
- ORCH：调度逻辑 + 异常矩阵

### 第五步：生成 LAUNCH.md（最关键）
必须包含以下模块，缺一不可：
- **任务性质**：必须完成，不是建议；不允许中途放弃/跳过/编造
- **完成定义 DoD**：具体可验证的条目（如"4 裁决点各 ≥20 样本实测完成"），不是模糊的"质量达标"
- **角色执行方式**：subagent 优先；无法调用时角色扮演但必须保持 QA/APP 分离
- **阻碍处理流程**：识别→自行修复（授权范围明确）→降级→写 BLOCKED→上报
- **不允许行为**：红线清单（不编数字、不跳实测、不静默降标准、不泄露 key 等）
- **具体操作步骤**：每步带具体命令、检查点、交付物路径

### 第六步：自检
- 每个角色的任务是否可执行（有具体命令/检查点，不是只有目标描述）
- 质量门是否有明确通过条件（可验证，不是"质量达标"）
- LAUNCH 指令是否包含完成定义和阻碍闭环
- 角色名是否和目标团队匹配
- 文件命名是否规范
- 是否有遗漏的交付物

## 产出物清单

每次生成 `docs/internal/harness-Mx/` 下的 8 个文件：

| 文件 | 用途 |
|------|------|
| `00-INDEX.md` | 总索引：角色体系、并行关系、质量门、交付物清单 |
| `Mx-My-总任务书.md` | 任务目标 + 验收标准 + 风险兜底 |
| `Mx-My-PM.md` | PM 角色指令：定标准 + 样本/方案设计 |
| `Mx-My-ENG.md` | ENG 角色指令：修配置 + 冒烟 |
| `Mx-My-APP.md` | APP 角色指令：主执行 + 出报告 |
| `Mx-My-QA.md` | QA 角色指令：独立验收 + 反作弊 |
| `Mx-My-ORCH.md` | ORCH 调度指令：3 质量门 + 异常矩阵 |
| `Mx-My-LAUNCH.md` | Claude Code 启动入口（含可直接复制的启动指令） |

## 模板使用

`templates/` 下有 8 个模板文件，生成时：
1. 用 `scripts/init_milestone.sh` 创建目录和文件骨架（自动替换里程碑编号等占位符）
2. 根据需求和目标团队角色定义，填充模板内容
3. 自检后交付

## 命名规范

- 目录：`docs/internal/harness-Mx/`（x 为里程碑编号，小写）
- 文件：`Mx-My-角色.md`（My 为子任务编号）
- LAUNCH 文件：`Mx-My-LAUNCH.md`
- 角色名用目标团队的实际前缀（如 `dome-*`、`hermes-*`）

## 质量标准

- LAUNCH.md 必须写到"操作手册"级别，让 Claude Code 没有歧义空间
- 每个角色指令必须有具体的可执行步骤，不能只有目标描述
- 质量门必须有可验证的通过条件
- 完成定义 DoD 必须是具体可检查的条目
- 阻碍处理流程必须明确：什么情况自行修复、什么情况降级、什么情况上报
- 团队定义文件（.claude/）不在本 Skill 修改范围内，任务指令只动 docs/internal/harness-Mx/
