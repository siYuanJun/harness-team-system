# PRD Review Orchestrator

将用户的"评审这份 PRD"请求，编排为四角色评审流水线。

**对话日志铁律**：评审全过程必须留痕。编排者在每个阶段结束后，按 `references/dialogue-log-protocol.md` 向 `10-dialogue-log.md` 追加记录——谁说了什么（🗣️）、确定了什么（✅）、理解了什么（🧠）、定性了什么（🏷️）。**先记录后流转**，日志未追加不得进入下一阶段。

## 触发条件

用户请求满足任一：
- 明确要求"评审 / review 一份 PRD / 需求文档 / 产品需求"
- 提供 PRD 文件路径并要求团队评审
- 说"启动 prd-review 团队"

## 前置检查

1. PRD 文件存在且可读（读不到先解决，不空转流程）
2. 如 PRD 未声明产品背景，且项目内有 README / AGENTS.md，一并读取作为行业判断输入
3. 创建输出目录：`.prd-reviews/{YYYY-MM-DD}-{prd文件名}/`（在项目根目录下）

## Phase 0 · 准备

- 完整读取 PRD（含图表说明文字）
- 记录：文档标题、章节结构、功能点数量、自带优先级/指标情况
- 写入 `00-prd-meta.md`
- 📝 **日志**：按协议创建 `10-dialogue-log.md`，写入文件头 + 首条 🧠 UNDERSTAND（团队对 PRD 的初始理解：主题、结构、评审范围）

## Phase 1 · 独立评审（并行，互不可见）

并行派发三个子任务，分别加载角色定义：

| 子任务 | 角色定义 | 输入 | 输出 |
|--------|----------|------|------|
| A | `prd-pm-industry.md` | PRD 全文 + 项目背景 | `01-review-pm1-industry.md` |
| B | `prd-pm-value.md` | PRD 全文 | `02-review-pm2-value.md` |
| C | `prd-pm-rationality.md` | PRD 全文 | `03-review-pm3-rationality.md` |

派发要求：
- 每个子任务只能看到自己的角色定义 + PRD 原文，**不得看到其他 PM 的产出**（防锚定）
- 每个子任务按角色定义中的输出格式产出
- 三份产出落盘后，编排者通读三份，提取"条目池"（每条意见编号 I1, V1, R1…）
- 📝 **日志**：每位 PM 的 🗣️ SAY 核心结论（各 1-3 条）+ 🏷️ LABEL 全部定性判断（痛点分级、价值评级、夸大标记、假设判定等，逐条记录并引用条目编号）

## Phase 2 · 圆桌辩论（固定 2 轮，禁止超过 2 轮）

**轮 1 · 交叉质疑**
- 每位 PM 读取另外两位的产出，对其中不认同的条目发起质疑（必须指明条目编号 + 质疑理由）
- 被质疑方必须回应：坚持（附新理由）/ 让步（修改结论）/ 部分接受
- 产出 `04-debate-round1.md`
- 📝 **日志**：每条质疑与回应各记 1 条 🗣️ SAY（质疑方+理由、被质疑方立场+理由）；让步导致的结论修订记新条目并注明推翻的旧条目

**轮 2 · 收敛表态**
- 每位 PM 输出最终立场清单：对每条核心意见标注 同意 / 有保留同意 / 反对（附一句话理由）
- 产出 `05-debate-round2.md`
- 📝 **日志**：每位 PM 对关键条目的最终立场各记 1 条 🗣️ SAY；辩论中新形成的共同理解记 🧠 UNDERSTAND

辩论协议细则见 `references/debate-protocol.md`。

## Phase 3 · 共识汇总

编排者按 `references/consensus-rules.md` 分类：
- **一致通过**（3/3 同意）
- **有保留同意**（2/3 及以上同意，保留意见记录在案）
- **分歧保留**（无法收敛，交技术经理仲裁）
产出 `06-consensus.md`
- 📝 **日志**：每条共识记 1 条 ✅ DECIDE（结论 + 通过比例）；分歧项记 🗣️ SAY 双方立场；分类过程中确认的事实前提记 🧠 UNDERSTAND

## Phase 4 · 技术经理裁决

- 派发子任务，加载 `prd-tech-lead.md`
- 输入：`06-consensus.md` + 三份 PM 评审（供查证）+ PRD 原文（仅供定位章节，不重新评审）
- 产出 `07-tech-verdict.md`（含最终 P0/P1/P2 修改清单）
- 📝 **日志**：每条裁决记 1 条 ✅ DECIDE（裁决类型 + 理由摘要，否决项必须含替代方案）；分歧仲裁的选边与理由记 ✅ DECIDE；技术补充项记 🏷️ LABEL（复杂度/成本定性）

## Phase 5 · 产出交付

1. 按 `templates/review-report.md` 组装 `08-review-report.md`
2. 从裁决中提取 `09-prd-change-list.md`（按 `templates/change-list.md`）
3. 📝 **日志**：追加 ✅ DECIDE 收尾条目（评审结论 + 交付物清单），为日志补上结束时间
4. 向用户交付：两份文件路径 + 对话日志路径 + 一段中文摘要（总体评价、P0 数量、最大分歧点）

## 边界与禁止

- ❌ 不修改 PRD 原文——只产出意见与清单；如用户明确要求改 PRD，另行确认后执行
- ❌ 辩论不超过 2 轮；第 2 轮后仍分歧的一律转技术经理仲裁
- ❌ 技术经理不重新评审 PRD 全文
- ❌ 中途任何角色发现 PRD 信息不足以判断时，列入"需作者澄清"，不得虚构事实填补
- ❌ 禁止跳过或事后补写对话日志——每阶段产出落盘后必须先追加日志再流转（见 `references/dialogue-log-protocol.md`）
