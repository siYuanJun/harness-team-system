# 共识分类与技术经理裁决规则

## 共识分类标准

以轮 2 收敛表态为准，编排者对每条核心意见分类：

| 分类 | 判定条件 | 流向 |
|------|----------|------|
| **一致通过** | 3/3 同意 | 技术经理裁决（默认同意，除非成本/复杂度否决） |
| **有保留同意** | ≥2 同意，存在保留意见 | 技术经理裁决（保留意见随条目附上） |
| **分歧保留** | 存在反对且未收敛 | 技术经理仲裁，必须拍板一方 |
| **需作者澄清** | 任一 PM 标注信息不足 | 不进入裁决，列入澄清清单交用户 |

## 技术经理裁决规则

对每条共识，裁决只能是四种之一：

| 裁决 | 含义 | 硬性要求 |
|------|------|----------|
| ✅ 同意 | 按共识修改 PRD | 修改建议必须具体到章节/语句 |
| 🔧 同意但修改 | 方向对，改法调整 | 附调整后的修改建议 |
| ⏬ 降级 | 优先级/范围降低 | 说明降级理由（成本/复杂度/依赖） |
| ❌ 否决 | 不采纳 | **必须附替代方案**，无一例外 |

## 修改清单优先级定义

| 级别 | 含义 | 判定来源 |
|------|------|----------|
| **P0 必改** | 不改则 PRD 不可进入开发 | 逻辑矛盾、伪痛点支撑的核心功能、夸大承诺、高风险边界遗漏 |
| **P1 建议改** | 影响评审通过质量 | 价值模糊、指标缺失、一般边界遗漏 |
| **P2 可选** | 锦上添花 | 措辞优化、补充说明 |

## 铁律

1. 每条裁决必须有"提出人"归属（PM1/PM2/PM3/技术补充）
2. 分歧仲裁禁止和稀泥——必须选边并说明理由
3. 复杂度 XL 条目默认降级或分期，除非价值理由特别强
4. 最终清单必须可直接执行：位置（PRD 章节）+ 问题 + 修改建议，三者缺一不算完整条目
