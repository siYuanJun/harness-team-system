# 团队维护机制

> 团队搭建完成不是终点。常驻团队会"脑腐"——角色职责和项目实际情况脱节。必须有维护机制。

## 什么是脑腐

团队定义文件（`.claude/agents/`、`CLAUDE.md`）如果不随项目演进而更新，会出现：
- 角色职责和项目实际工作不匹配
- 路由表指向不存在的角色或错误的角色
- pm 的大脑基座（领域知识）过时
- 编排器的 Phase 流程和实际开发流程脱节
- 知识库（knowledge-keeper 的产出）未更新

后果：AI 看着过期信息，越用越笨。

## 什么时候必须更新团队定义

| 触发条件 | 需要更新什么 |
|----------|-------------|
| 项目技术栈重大变化 | 相关角色的职责描述、pm 的设计红线 |
| 新增角色职责或角色职责变化 | `.claude/agents/` 对应文件、路由表 |
| 路由表失效（某类指令不再路由到原角色） | `CLAUDE.md` 路由表、编排器路由规则 |
| 项目规模变化需要调整团队分级 | 团队规模升级/降级、新增/移除角色 |
| 新增 Worktree 并行需求 | 编排器增加 Worktree 调度、新增 merge-engineer |
| 项目目标重大变化 | pm 的 PRD 模板、验收标准、编排器 Phase 流程 |

## 维护流程

### 定期维护（推荐每 2-4 周一次）

1. **触发**：用 `neat-freak` Skill 跑 `/neat`，检查文档、CLAUDE.md、Agent 记忆的对齐情况
2. **发现问题**：neat-freak 会列出不对齐的项
3. **更新**：orchestrator 或人更新团队定义文件
4. **验证**：触发几个典型指令，确认路由正确
5. **记录**：在 CLAUDE.md 的变更记录里写明更新内容和时间

### 事件驱动维护（触发条件出现时立即做）

1. 识别触发条件（见上表）
2. 更新对应文件
3. git 提交（conventional commits，scope 标 `team-config`）
4. 通知团队（在 PROGRESS.md 记录）

## CLAUDE.md 必须包含的维护区块

```markdown
## 团队维护记录

| 日期 | 更新内容 | 原因 |
|------|----------|------|
| 2026-09-06 | 初始搭建，7 角色标准团队 | 项目启动 |
| YYYY-MM-DD | 新增 merge-engineer，启用 Worktree 并行 | 项目规模扩大 |

## 下次维护检查项
- [ ] 路由表是否还有效
- [ ] 角色职责是否和项目实际匹配
- [ ] pm 的领域知识是否需要更新
- [ ] 知识库是否需要沉淀新内容
```

## 维护的边界

- **可以更新**：角色职责描述、路由表、编排器流程、pm 的大脑基座
- **不可以随意更新**：核心铁律（管流程不管质量）、角色间的分离原则（执行和验收分离）
- **需要人确认**：团队分级变更（升级/降级）、新增/移除核心角色

## 和 neat-freak 的配合

`neat-freak` Skill 负责检测脑腐（文档/CLAUDE.md/记忆不对齐），本机制负责修复脑腐（更新团队定义）。两者配合：
- neat-freak 发现问题 → 本机制更新团队定义 → neat-freak 验证对齐

## 反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|----------|
| 搭完就不管 | 3 个月后团队定义完全过时 | 定期维护，事件驱动更新 |
| 只更新代码不更新团队 | 代码迭代了七八轮，角色定义还是最初版 | 代码重大变更时同步更新团队 |
| 维护不记录 | 不知道什么时候改了什么、为什么改 | CLAUDE.md 维护记录区块 |
| 过度维护 | 每天改角色定义，团队不稳定 | 定期（2-4周）+ 事件驱动，不频繁 |
