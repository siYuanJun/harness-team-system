# 角色定义文件规范

> 每个 `.claude/agents/<角色>.md` 必须包含以下章节。这是团队不空壳的基础。

## 文件结构

```markdown
---
name: {team}-{role}          # 角色名，如 dome-pm
description: 一句话职责描述    # 用于路由匹配
model: opus                  # 运行时模型指定
---

# {角色名} · {角色中文名}

## 核心角色
你是谁，在团队中的定位。

## 工作原则
3-5 条不可违反的原则。如：
- 管流程的不管质量
- 不编造数据
- 遇到阻碍先自行修复，修复不了上报

## 输入
你接收什么类型的任务和信息。

## 输出
你产出什么交付物，放在什么路径。

## 协作
- 你向谁汇报：orchestrator
- 你和谁交接：下一环角色
- 你不碰什么：其他角色的职责

## 团队通信协议
- 任务接收方式：orchestrator 分派
- 进度汇报方式：PROGRESS.md
- 异常上报方式：BLOCKED.md

## 错误处理
遇到错误时的处理流程：
1. 自行修复（授权范围内）
2. 重试 1 次
3. 仍失败 → 记录错误，上报 orchestrator
```

## 必须包含的要素

- [ ] frontmatter：name、description、model
- [ ] 核心角色：明确的定位，不模糊
- [ ] 工作原则：可执行的原则，不是空话
- [ ] 输入输出：明确的类型和路径
- [ ] 协作关系：向谁汇报、和谁交接、不碰什么
- [ ] 错误处理：具体的处理流程

## 反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|----------|
| 只有标题没有内容 | 角色是空壳，AI 不知道该干什么 | 每个章节都有具体内容 |
| 职责描述模糊 | "负责产品相关工作"——什么是产品相关？ | 具体到："把模糊需求转化为 PRD 和验收标准" |
| 多个角色职责重叠 | acceptor 和 reviewer 都做审校 | 明确分工：acceptor 验收交付物，reviewer 审内容质量 |
| 没有错误处理 | 遇到错误不知道怎么办 | 写清重试、降级、上报的流程 |
| 没有 model 字段 | Claude Code 不知道用什么模型跑 | frontmatter 加 `model: opus` |
| description 太泛 | "帮助团队"——路由匹配不到 | 写具体触发词，如"验收/测试/终验" |
