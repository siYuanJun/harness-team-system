# 搭建质量门标准

> 团队搭建完成的验收标准。全部满足才算搭建完成，不允许"差不多就行"。

## 质量门清单

### G1：角色定义完整性

- [ ] `.claude/agents/` 目录存在
- [ ] 每个选定角色都有对应的 `.md` 文件
- [ ] 每个文件 frontmatter 包含：name、description、model
- [ ] 每个文件包含：核心角色、工作原则、输入、输出、协作、错误处理
- [ ] 角色职责不重叠（每个角色有明确边界）
- [ ] 执行角色和验收角色分离（没有角色自己执行自己验收）

### G2：编排器完整性

- [ ] `.claude/skills/{team}-orchestrator/SKILL.md` 存在
- [ ] 包含路由表（触发词 → 角色 → 干什么）
- [ ] 包含 Phase 流程（阶段划分 + 质量门位置）
- [ ] 包含数据传递协议（角色间通过文件交接）
- [ ] 包含错误处理流程
- [ ] 如启用 Worktree：包含 Worktree 调度逻辑
- [ ] `references/roadmap.md` 存在（项目状态底稿）

### G3：CLAUDE.md 完整性

- [ ] 根目录 `CLAUDE.md` 存在
- [ ] 包含触发规则（什么指令触发团队模式）
- [ ] 包含路由表（和编排器一致）
- [ ] 包含团队维护记录区块
- [ ] 包含变更记录
- [ ] 包含核心铁律（管流程不管质量等）

### G4：配置正确性

- [ ] 所有文件 frontmatter 合法（YAML 格式正确）
- [ ] 没有多余的 `.claude/commands` 目录（如果用了 commands，需确认是有意的）
- [ ] 角色名和路由表中的引用一致
- [ ] 文件编码为 UTF-8

### G5：可触发性验证

- [ ] 至少触发 3 个典型指令，确认路由到正确角色
- [ ] 模糊指令能被 orchestrator 正确拆分
- [ ] 不存在"触发词指向不存在的角色"的情况

### G6：Git 提交

- [ ] 团队配置文件已 git add
- [ ] 按 conventional commits 提交（scope 标 `team-config`）
- [ ] 提交信息清晰描述搭建内容

### G7：团队规模合理性

- [ ] 团队规模（最小/标准/扩展）与项目复杂度匹配
- [ ] 不是盲目满配（小项目不用扩展团队）
- [ ] 不是过度精简（大项目不用最小团队）

### G8：维护机制就绪

- [ ] CLAUDE.md 包含团队维护记录区块
- [ ] 记录了下次维护检查项
- [ ] 明确了维护触发条件

## 验收方式

每条质量门必须有实际验证，不允许"我觉得没问题"：

- G1：逐个文件检查，用 `ls .claude/agents/` 和 `head` 命令验证
- G2：读编排器文件，确认每个章节存在
- G3：读 CLAUDE.md，确认每个区块存在
- G4：用 YAML 解析器或人工检查 frontmatter
- G5：实际触发指令，观察路由结果
- G6：`git log --oneline -1` 确认提交
- G7：对照 `team-sizing.md` 的选型信号判断
- G8：检查 CLAUDE.md 的维护记录区块

## 不通过的处理

- 任何一条不通过 → 修复后重新验证
- G1-G4 不通过 → 团队是空壳，必须修复
- G5 不通过 → 路由有问题，必须修复
- G7 不通过 → 团队规模不合理，调整后重新验证
- 不允许"先交付后修复"——团队配置是基础设施，必须一次到位
