# 6 种团队架构模式（harness-main 蒸馏）

> 来源：revfactory/harness 插件。蒸馏 6 种架构模式的适用场景、结构和选型决策。

## 模式总览

| 模式 | 结构 | 适用场景 |
|------|------|----------|
| Pipeline（流水线） | 顺序依赖，A→B→C | 有明确先后顺序的任务，如本体建模六环 |
| Fan-out/Fan-in（扇出扇入） | 并行独立任务，最后整合 | 可并行的独立子任务，如代码审查多维度并行 |
| Expert Pool（专家池） | 按上下文选择性调用专家 | 任务类型多样，每次需要不同专家 |
| Producer-Reviewer（生产者-审校者） | 生成→质量审查→迭代 | 内容创作、文档、代码，需要质量把关 |
| Supervisor（监督者） | 中心 Agent 动态分配任务 | 任务不确定，需要动态调度 |
| Hierarchical Delegation（层级委派） | 自上而下递归委派 | 大型复杂任务，需要分层管理 |

## 详细说明

### 1. Pipeline（流水线）

**结构**：A 完成 → B 接手 → C 接手，每环有质量门。

**适用**：
- 任务有明确先后顺序
- 每环产出是下一环的输入
- 需要每环独立验收

**例子**：本体建模六环（术语→概念→Schema→实例→RAG→评测）。

**优点**：流程清晰，质量门可控。
**缺点**：串行，效率低；一环卡住全链阻塞。

### 2. Fan-out/Fan-in（扇出扇入）

**结构**：中心拆分任务 → 多个 Agent 并行执行 → 中心整合结果。

**适用**：
- 任务可拆成独立子任务
- 子任务之间无依赖
- 需要多视角覆盖

**例子**：代码审查（架构/安全/性能/风格四维度并行）、竞品分析（多公司并行调研）。

**优点**：并行效率高，多视角覆盖。
**缺点**：整合难度大；子任务粒度难把握。

### 3. Expert Pool（专家池）

**结构**：一组专家 Agent，按任务上下文选择性调用。

**适用**：
- 任务类型多样
- 每次只需要其中几个专家
- 专家之间相对独立

**例子**：技术咨询团队（前端专家/后端专家/数据库专家/安全专家，按问题选）。

**优点**：灵活，按需调用，不浪费资源。
**缺点**：路由判断要准；专家之间协作少。

### 4. Producer-Reviewer（生产者-审校者）

**结构**：Producer 生成 → Reviewer 审查 → 反馈 → Producer 迭代。

**适用**：
- 内容创作（文章、文档、代码）
- 需要质量把关
- 可迭代优化

**例子**：写 PRD（pm 写 → reviewer 审 → pm 改）、写代码（engineer 写 → acceptor 测 → engineer 修）。

**优点**：质量有保障，可迭代。
**缺点**：多一轮交互，耗时；审校标准要明确。

### 5. Supervisor（监督者）

**结构**：中心 Supervisor 动态分配任务给 Worker，监控进度，整合结果。

**适用**：
- 任务不确定，需要动态调整
- Worker 能力不同，需要匹配
- 需要全程监控

**例子**：项目管理（orchestrator 动态派活，根据进度调整）。

**优点**：灵活，适应性强。
**缺点**：Supervisor 成为瓶颈；决策质量依赖 Supervisor。

### 6. Hierarchical Delegation（层级委派）

**结构**：顶层 → 中层 → 底层，递归委派，每层管理下一层。

**适用**：
- 大型复杂任务
- 需要分层管理
- 任务可递归拆分

**例子**：大型系统开发（架构师→模块负责人→开发者）。

**优点**：可扩展，管理大规模团队。
**缺点**：层级多，信息传递损耗；协调复杂。

## 选型决策树

```
任务有明确先后顺序？
├─ 是 → Pipeline
└─ 否 → 任务可拆成独立子任务并行？
     ├─ 是 → Fan-out/Fan-in
     └─ 否 → 任务类型多样，每次需要不同专家？
          ├─ 是 → Expert Pool
          └─ 否 → 需要质量把关和迭代？
               ├─ 是 → Producer-Reviewer
               └─ 否 → 任务不确定，需要动态调度？
                    ├─ 是 → Supervisor
                    └─ 否 → 大型复杂，需要分层？
                         ├─ 是 → Hierarchical Delegation
                         └─ 否 → 混合模式（如 Supervisor + Pipeline）
```

## 混合模式

实际项目常使用混合模式。例如：
- **Supervisor + Pipeline**：orchestrator 监督，执行走流水线
- **Fan-out + Producer-Reviewer**：并行生成，每个都有审校
- **Pipeline + Fan-out**：某一环内部并行（如 Schema 设计环内，多个领域并行）

ontology-dome-team 用的是 **Pipeline + Producer-Reviewer**：六环流水线，每环后有 QA 独立验收。
