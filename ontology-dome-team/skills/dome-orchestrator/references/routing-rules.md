# 路由规则

## 一级路由（入口判断）

用户的话属于哪类任务，直接决定怎么调度。

### 全流程任务

**触发词**：跑流水线、开始六环、做本体建模、完整走一遍、六环全跑

**路由**：Orchestrator 全流程调度
- Phase 0 任务拆解
- Phase 1 环①② + QA
- Phase 2 环③④ + QA
- Phase 3 环⑤⑥ + QA
- Phase 4 汇总交付

**前置条件**：有明确的业务文档输入。

### 单环 / 部分环任务

| 触发词 | 路由 | 输入要求 |
|--------|------|---------|
| 术语提取 / 环①② / 业务调研 | 业务调研 Agent 直接执行 | 业务文档 |
| 建 Schema / 环③ / 本体建模 | 本体建模 Agent 直接执行 | scope 数据 + 文档 |
| 灌实例 / 环④ / 数据映射 | 本体建模 Agent 直接执行 | Schema + 文档 |
| RAG 接入 / 环⑤ | 应用对接 Agent 直接执行 | Schema + 实例 |
| 评测 / 环⑥ / 对比一下 | 应用对接 Agent 直接执行 | RAG 代码 + 实例 |
| 验收 / 检查质量 / pass了吗 | QA 验收官直接执行 | 待验收产物 + 环号 |

### 产品 / 需求任务

**触发词**：需求、PRD、方案、规划、怎么做、优先级、方向、竞品

**路由**：PM 产品经理直接执行（产出 PRD + 验收标准 + 优先级，交 Orchestrator 分派执行）

### 工程任务

**触发词**：提交代码、git、push、环境、装依赖、打 tag

**路由**：Engineer 工程手直接执行

### 状态查询

**触发词**：进度、状态、怎么样了、总览

**路由**：Orchestrator 直接回答（读 PROGRESS.md + PENDING.md）

### 模糊 / 跨角色任务

**触发词**：说不清具体要什么、涉及多个环节、新需求

**路由**：Orchestrator 先理解 → 拆子任务 → 分派 → 整合

## 二级路由（质量门）

每环结束后必须经过 QA 验收，这不是可选的，是强制的。

- 每环产出 → QA 验收 → PASS → 进下一环
- 每环产出 → QA 验收 → FAIL → 退回修改

QA 验收是独立的，Orchestrator 不能干预结论，只能按结论走流程。

## 三级路由（异常）

| 异常类型 | 路由 |
|----------|------|
| 执行失败 / 产出不合格 | 退回对应执行 Agent |
| 接口断裂 / 上下游对不上 | Orchestrator 协调双方 |
| 环境 / 依赖 / git 问题 | Engineer 工程手 |
| 需求不清 / 范围争议 | 等 Human 裁决 |
| 连续失败 / 阻塞问题 | 停 + BLOCKED.md + Human 决策 |

## 路由优先级

1. **明确的单角色任务** → 直接派给对应角色（最快路径）
2. **明确的多角色任务** → Orchestrator 调度串起来
3. **模糊任务** → Orchestrator 先拆解再分派
4. **工程杂务** → Engineer 工程手（不打扰专业角色）
5. **质量问题** → QA 验收官（独立通道，不经过执行角色）

## 路由反模式（不要这么干）

- ❌ 让 QA 去改代码（QA 是裁判不是运动员）
- ❌ 让执行 Agent 自己验收自己的产出（既当运动员又当裁判）
- ❌ 让 Engineer 改业务逻辑（工程手不越界业务）
- ❌ Orchestrator 自己动手干执行的活（总监下场写代码 = 团队架构崩了）
- ❌ 模糊任务直接扔给某个角色（先拆清楚再派）
