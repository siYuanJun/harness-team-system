# 质量门标准

六环流水线有三道质量门（每两环一道），每道门都由 QA 验收官独立执行。

## 质量门一：环①② → 环③

**检查对象**：术语表 + 范围清单

### 必过项（不通过不许进下一环）

- [ ] 术语表格式正确，每个术语有来源
- [ ] 消歧规则清晰可执行
- [ ] 范围清单结构合法（classes / relations / attrs 齐全）
- [ ] 每个类候选有原文依据
- [ ] 不建清单有理由（不是漏了）
- [ ] 返回的 JSON 结构符合约定
- [ ] PENDING 项有记录（空的也写"无"）

### 暗卷抽查

- 泛化测试：换非保险域文档 → 不崩、不硬套
- 边界测试：空输入 → 干净返回 empty
- 重复检测：有没有大量重复或灌水

### 反作弊检查

- 没有硬编码的术语 / 概念列表
- 消歧规则真的生效（不是摆设）
- scope 是从术语表推导出来的，不是凭空写的

## 质量门二：环③④ → 环⑤

**检查对象**：Schema + 实例库

### 必过项

- [ ] validate_ontology.py 校验 PASS
- [ ] 命名规范统一（PascalCase / camelCase / 动词短语）
- [ ] 中英映射完整（每个元素都有 label_cn + description）
- [ ] Schema 和 scope 对应（scope 里有的都建了，没多加）
- [ ] 实例结构合法（类存在、属性类型对、关系两端存在）
- [ ] 每个实例有来源标注
- [ ] PENDING 项有记录

### 暗卷抽查

- 结构深度合理（不过度建模也不太浅）
- 关系完整性（有没有明显漏掉的反向关系）
- 实例覆盖率（重要的类有没有实例）
- 来源真实性（抽查几个实例对原文）

### 反作弊检查

- validate 没有被绕过（`|| true` / 注释 / mock）
- Schema 不是硬编码的（从 scope 驱动）
- 实例不是"复制粘贴改名"的假实例

## 质量门三：环⑤⑥ → 交付

**检查对象**：RAG 代码 + 评测报告

### 必过项

- [ ] RAG 代码语法正确、可运行
- [ ] 有本体 / 无本体双模式都存在
- [ ] 评测数字完整（P / R / F1 / 串险种率 / Δ）
- [ ] 评测方法描述清楚
- [ ] eval_result.json 结构完整
- [ ] PENDING 项有记录

### 暗卷抽查（最严！）

- **重跑验证**：亲手跑一遍，数字对得上
- **基线公平性**：两种模式除了本体外参数一致
- **串险种率真实性**：真的独立测的，不是凑的
- **数据泄露检测**：有本体模式有没有偷看答案
- **评测集来源**：从实例库派生的，不是硬编码的

### 反作弊检查（红线）

- 评测集不是硬编码的 → 抽查 3 个问题对实例库
- 有本体模式没有数据泄露 → 代码审查
- 基线没有被故意调差 → 参数对比
- 数字不是写死的 → 重跑一致

## 严重度分级

- **P0 阻断**：必过项不通过 / 反作弊红线
- **P1 重要**：暗卷发现问题，但不阻塞主流程
- **P2 一般**：小瑕疵、体验问题、文档问题

## 退回规则

| 轮次 | 处理 |
|------|------|
| 第 1 次不通过 | 退回修改，附完整问题清单 |
| 第 2 次不通过 | 再退回，附对比（这次改了什么、还剩什么） |
| 第 3 次不通过 | 关键环 → 停 + BLOCKED；非关键环 → 降级 STUB + PENDING |

降级 STUB 的产物会标记 `STUB_` 前缀，明确告诉下游"这是桩，别当真"。
