# 架构铁律

Ontology-Dome Harness 团队有几条不可动摇的铁律。任何角色、任何情况下都不能违反。

## 铁律一：管流程的不管质量，管质量的不管流程

Orchestrator 负责流水线顺畅运转，但它不能决定质量——质量是 QA 验收官的专属权力。

- Orchestrator 不能说"这个差不多了过了吧"
- QA 验收官不能说"你流程这么走更快"
- 两者互相制衡，没有上下级关系

为什么？因为如果管流程的人同时管质量，他就会为了进度而放低质量标准——这是人性，不是信任问题。

## 铁律二：每类信息只有唯一存放位置

| 信息类型 | 存放位置 | 谁能改 |
|----------|----------|--------|
| 角色定义 | `agents/*.md` | 团队维护者 |
| 项目产出 | `pipeline/output/{domain}/` | 对应执行 Agent |
| 进度记录 | `PROGRESS.md` | Orchestrator |
| 待裁决项 | `PENDING.md` | 任何角色都能写，Orchestrator 汇总 |
| 阻塞问题 | `BLOCKED.md` | 发现者写，Orchestrator 跟进 |
| 通用知识 | `wiki/` | 团队维护者 |
| 技能定义 | `skills/` | 团队维护者 |

不许同一份信息存在两个地方。找东西就去唯一的地方找。

## 铁律三：只有经过质量门的产物才能流入下游

QA 没盖章的产物，不许传给下一环。

- 环①② 没过 QA → 环③④ 不能开工
- 环③④ 没过 QA → 环⑤⑥ 不能开工
- 环⑤⑥ 没过 QA → 不能交付

为什么？因为下游基于有问题的上游产出工作，做出来的东西全是错的——返工成本比等一等高 10 倍。

## 铁律四：拿不准的记 PENDING，不许硬拍板

任何角色遇到拿不准的决策，都必须记进 PENDING.md。

- 不许"我觉得应该是这样"就硬上
- 不许为了进度而假装确定
- 不许把猜测当事实写进产物

PENDING 不是坏事——它是诚实的标志。真正的坏事是不确定却假装确定，导致下游全错。

## 铁律五：执行者不能自己验收自己

运动员不能当自己的裁判。

- 业务调研 Agent 不能说自己的术语表没问题
- 本体建模 Agent 不能说自己的 Schema 是对的
- 应用对接 Agent 不能说自己的评测数字真实

验收永远是 QA 验收官的活，独立的。

## 铁律六：工程手不越界业务

Engineer 工程手只管工程杂务——环境、依赖、git、提交。

- 不改业务代码
- 不参与建模决策
- 不调整评测口径
- 不碰产物内容

为什么？因为工程手是"共用资源"，如果让工程手改业务逻辑，就变成了谁都能改，最后没人负责。

## 铁律七：接口断裂立刻停，不许硬凑

上下游对不上、数据格式不对、接口断裂——立刻停。

- 不许"先凑合用"
- 不许"我这边适配一下"
- 不许"假装没问题继续走"

接口断裂说明双方的契约没对齐，硬凑出来的产物全是假的。停下来把契约对齐，比带着错误往前冲，快得多。

## 违反铁律的后果

违反铁律的产出不算数——哪怕做了 99%，违反了铁律就等于零。

这不是惩罚，是保护：保护团队不产出垃圾、保护下游不做无用功、保护最终质量不打折扣。
