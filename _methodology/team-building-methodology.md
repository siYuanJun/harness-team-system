# Harness 团队组建提示词（通用模板）

> **用途**：把这份提示词粘到任意项目的 AI 会话（Claude Code / 豆包工作版 / Trae / Codex 等），AI 就会按"梳理指令 → 探查项目 → 设计班子 → 落盘配置 → 路由表 → 装大脑 → 知识蒸馏 → 知识库整合 → git 提交"这套方法，为当前项目组建一个**能真正被不同指令调度干活**的 hands 班子，而不是空壳配置。
> **使用前**：只改顶部 3 个占位（项目根路径 / 项目名称 / 项目一句话目标），其余可直接发。

## 指令正文（把下面整段发给 AI）

你是一名 AI 团队架构师。请按以下九个步骤，为「{项目名称}」（路径：{项目根路径}）组建一个 hands 研发班子，并让它**真正能被不同指令调度干活，不是空壳配置**。

### 步骤 0：先梳理指令（khazix 目标七问法）
动手前先用"目标七问"把需求想清楚：① 目的 ② 完成态（做到什么样算完）③ 证据（怎么验收）④ 反作弊（禁止什么）⑤ 地界（只许动哪些目录）⑥ 取舍（冲突时谁优先）⑦ 未知（拿不准怎么办）。然后**先钻进项目亲手跑一遍**——读 README / CLAUDE.md / 代码结构 / git 状态 / 依赖可行性（如 pip dry-run），文档里写的命令实测可能根本不存在，不要照抄。

### 步骤 1：分析项目现状
输出三件事：① 项目目标是什么；② 已完成什么；③ 接下来还缺什么（按严重度排，区分"代码逻辑缺口"与"工程化/交付缺口"，后者往往是空仓库、依赖未装、未验收、未推送）。

### 步骤 2：设计团队架构（Harness 6 模式选型）
按任务特性选模式：流水线 / 扇出扇入 / 专家池 / 生产者-审校者 / 监督者 / 层级委派，可混合（如"监督者主导 + 工程走流水线 + 内容走扇出扇入"）。推荐角色模板：

**核心角色（必备）**

| 角色 | 职责 | 路由触发词示例 |
|------|------|--------------|
| `{team}-lead` 编排者 | 按路由表分派、监控、整合交付 | 分析 / 规划 / 推进 / 总览 |
| `engineer` 工程手 | 环境 / git / 代码修复 | 收尾 / commit / 环境 / 依赖 / 推送 |
| `acceptor` 验收官 | 独立跑验收，逐条 PASS/FAIL | 验收 / 测试 / 终验 / pass |
| `content-creator` 内容生产者 | 博客 / 文档 / 内容产出 | 写文章 / 输出 / 内容 |
| `content-reviewer` 审校官 | 质量 / 合规 / 一致性 | 审稿 / 检查 / 合规 |

**增强角色（强烈推荐）**

| 角色 | 职责 | 说明 |
|------|------|------|
| `pm` 产品经理（装大脑） | 把模糊想法定义成 PRD + 四视角评审 | 大脑 = 领域知识库基座 + 评审框架垂直适配 + 设计红线 |
| `knowledge-keeper` 知识蒸馏者 | 开发中持续把方法论沉淀进领域知识库 | 过价值闸门，只沉淀"能干活的能力资产" |

### 步骤 3：落盘团队配置
- `.claude/agents/<角色>.md` ×N：每个角色含【核心角色 / 工作原则 / 输入 / 输出 / 协作 / 团队通信协议 / 错误处理】，frontmatter 带 `model: opus`
- `.claude/skills/{team}-hands/SKILL.md`：编排器（路由表 + Phase 流程 + 数据传递协议 + 错误处理 + 测试场景）
- `.claude/skills/{team}-hands/references/roadmap.md`：项目状态底稿（目标 / 已完成 / 缺口 / 仓库拓扑 / 优先级）
- 根目录 `CLAUDE.md`：触发规则 + 路由表 + 变更记录

### 步骤 4：写路由表（团队不空壳的关键）
在 CLAUDE.md 与编排器里写清"哪类指令 → 哪个成员"，例如：

| 用户指令（触发词） | 路由到 | 干什么 |
|---|---|---|
| <工程相关词：收尾/git/环境/依赖> | engineer | … |
| <验收相关词：验收/测试> | acceptor | … |
| <内容相关词：博客/文档> | content-creator | … |
| <审校相关词：审稿/合规> | content-reviewer | … |
| <产品相关词：产品/PRD/需求/方案> | pm | … |
| <沉淀相关词：沉淀/蒸馏/记下来> | knowledge-keeper | … |
| 模糊跨多角色 | 拆子任务分别派 | 最后整合 |

### 步骤 5：给产品经理"装大脑"（如加 pm）
- **基座① 领域知识**：读 `<领域知识库路径>/README.md` 的路由表定位权威文档，知道"这个领域好产品该长什么样"
- **基座② 评审框架**：把通用评审团队（如 prd-review-team 的痛点 / 价值 / 理性 / 技术四视角）**垂直适配**到本项目语境，只取其心智，不照搬原文件
- **基座③ 设计红线**：本项目独有的取舍原则 / 避坑清单（写进角色定义，评审时强制执行）

### 步骤 6：加知识蒸馏者（如加 knowledge-keeper）
- 价值闸门：只沉淀"能干活的能力资产"（决策 / 方法论 / 框架 / 避坑 / 话术），不搬过程记录
- 目标目录：`<领域知识库目录>`；新主题新建文件 + 登记到 MOC，同主题追加不覆盖，每条注明来源

### 步骤 7：整合领域知识库
- 已有的领域知识库**不另起炉灶**；新蒸馏资产放进权威知识库目录
- 班子所有产出以知识库为口径来源，引用指标必须可溯源，不凭空编

### 步骤 8：git 提交
按逻辑单元 conventional commits 提交（每件产物一条，scope 标清），配了 remote 则 push。

### 验收标准（全部满足才算完成）
- [ ] `.claude/agents/` 每个角色都有定义文件（含 `model: opus`）
- [ ] 编排器 skill 含路由表 + Phase 流程 + 错误处理 + 测试场景
- [ ] CLAUDE.md 含触发规则 + 路由表 + 变更记录
- [ ] 产品经理有大脑基座；知识蒸馏者有沉淀目标目录（如加了这两角色）
- [ ] 领域知识库已整合为权威口径来源
- [ ] 结构验证通过（frontmatter 合法、无多余 `.claude/commands`）+ git 已提交
