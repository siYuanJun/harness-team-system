# 架构铁律

Hermes Agent Team v3.0 的核心架构原则。

## 铁律一：管流程的不能管质量

**定义**：Coordinator 负责流程管理，Editor 负责质量审计，两者完全分离。

**原因**：
- 单一 Agent 同时负责流程和质量时，会优先关注进度、弱化质量检查
- 分离后形成制衡机制，确保质量不被牺牲

**实现**：
- Coordinator 不做事实核查、不做发布检查
- Editor 不管任务进度、不管资源分配
- 两者独立向 Human 报告

## 铁律二：每类信息只有唯一存放位置

**定义**：Profile/Project/Wiki/Session 四层数据严格隔离。

| 概念 | 存放位置 | 生命周期 | 内容 |
|------|----------|----------|------|
| **Profile** | `.claude/agents/hermes-*.md` | 永久 | 角色定义、行为原则 |
| **Project** | `.ai-workflow/hermes/projects/{id}/` | 项目周期 | 任务产出、中间数据 |
| **Wiki** | `hermes-agent-team/wiki/` | 永久 | 通用知识、架构规则 |
| **Session** | 对话上下文 | 会话周期 | 当前状态、临时数据 |

**原因**：
- 错放会导致系统记忆污染
- 唯一位置便于维护和检索
- 避免信息冗余和不一致

## 铁律三：只有绿色数据可流入下游

**定义**：三级置信度体系是源头阻断机制。

| 级别 | 颜色 | 流转规则 |
|------|------|----------|
| L1 | 🟢 绿色 | 可流入下游 |
| L2 | 🟡 黄色 | 需标注，不可作为核心依据 |
| L3 | 🔴 红色 | 禁止流入下游 |

**原因**：
- 在源头阻断编造
- 确保下游使用的是经过验证的数据
- 提供可追溯的质量保证

## 铁律四：Editor 独立验证

**定义**：Editor 不依赖 Researcher 的数据，独立搜索核实。

**原因**：
- 避免确认偏误
- 提供双重保障
- 可能发现 Researcher 遗漏的问题

**实现**：
- Editor 使用 WebSearch 独立搜索
- 查找不同于 Researcher 的来源
- 记录验证过程和来源

## 铁律五：Human 拥有最终决策权

**定义**：Human 在关键节点介入，拥有最终决策权。

**介入节点**：
1. 任务启动 — 确认目标和范围
2. 审计问题 — 决定是否接受产出
3. 数据不足 — 决定继续研究还是调整范围
4. 最终验收 — 确认交付

**原因**：
- AI 不能替代人类决策
- 关键决策需要人类判断
- 不打断每步流程，只在关键节点介入

## 违反铁律的后果

| 违反 | 后果 |
|------|------|
| Coordinator 做质量审计 | 质量被牺牲，流程优先 |
| 信息错放位置 | 系统记忆污染，信息不一致 |
| 使用非绿色数据 | 编造风险，质量不可控 |
| Editor 依赖 Researcher | 确认偏误，双重保障失效 |
| Human 不介入 | 缺乏最终把关，决策风险 |

## 铁律的执行

1. **角色定义** — 在 agents/*.md 中明确职责边界
2. **流程设计** — 在 SKILL.md 中定义交接协议
3. **质量检查** — Editor 独立验证
4. **人类监督** — Human 在关键节点介入
